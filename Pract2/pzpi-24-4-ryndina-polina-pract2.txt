3 ОПИС ВИКОНАНОЇ РОБОТИ
     3.1 Метод рефакторинґу Add Parameter
     Метод Add Parameter використовується тоді, коли наявних аргументів функції недостатньо для виконання її оновлених завдань [1, 4]. У такому випадку до переліку параметрів додається новий аргумент, через який передаються необхідні для обчислень дані [4].
     Потреба в такій зміні може виникнути під час розвитку програмного забезпечення, коли одна й та сама функція повинна враховувати різні вхідні умови [3, 4]. Наприклад, розрахунок вартості товару може залежати від розміру знижки, який відрізняється для кожного клієнта [4]. Передавання такого значення через аргумент функції дозволяє уникнути використання постійних значень безпосередньо в її реалізації та робить спосіб обчислення зрозумілішим [1].
     Для демонстрації цього прийому було розглянуто функцію calculate_final_price (додаток В, розділ В.1). У початковому варіанті розмір знижки визначався всередині функції та становив 5 %. Через це змінити відсоток знижки без редагування самої функції було неможливо [4].
     Під час рефакторинґу до функції додано аргумент discount_rate, який відповідає за величину знижки (додаток В, розділ В.2). Тепер потрібне значення можна передавати безпосередньо під час виклику функції. Також передбачено перевірку допустимого діапазону цього параметра. У результаті функція може використовуватися для різних умов розрахунку без зміни її внутрішньої реалізації [1, 4]. Слайд презентації зображено на рисунку Б.2 та Б.3.

     3.2 Метод рефакторинґу Remove Parameter
     Remove Parameter застосовується для спрощення інтерфейсу функції шляхом усунення аргументів, які не потрібні для її роботи [1, 4]. Якщо метод не використовує певний параметр або необхідні відомості вже доступні через інші об'єкти, передавання такого аргументу стає зайвим [4].
     Зайві параметри збільшують кількість даних, які потрібно враховувати під час виклику функції [3]. Крім того, вони можуть вводити в оману інших розробників, оскільки створюють враження, що передане значення впливає на виконання операції [4]. Видалення таких аргументів допомагає зробити інтерфейс функції простішим та залишити в ньому лише необхідні залежності [1].
     Приклад використання цього методу наведено на функції process_user_order (додаток В, розділ В.3). Спочатку вона отримувала два аргументи: об'єкт замовлення та окреме значення дати. Проте під час аналізу реалізації було виявлено, що дата вже зберігається в полі date самого об'єкта order [4].
     Тому під час рефакторинґу аргумент order_date було виключено з оголошення функції (додаток В, розділ В.4). Звернення до дати залишилося без змін, оскільки вона й надалі отримується з об'єкта замовлення [4]. Це дозволило усунути повторне передавання однієї й тієї самої інформації та скоротити кількість аргументів під час виклику функції [1]. Слайд презентації зображено на рисунку Б.4 та Б.5.

     3.3 Метод рефакторинґу Remove Control Flag
     Remove Control Flag - це прийом рефакторинґу, за допомогою якого усувають додаткові булеві змінні, що використовуються для визначення моменту завершення циклу або переходу до іншої частини алгоритму [1, 4].
     У деяких реалізаціях програмісти створюють змінну типу boolean, щоб запам'ятати, чи відбулася певна подія під час виконання циклу [4]. Надалі значення цієї змінної перевіряється для визначення подальших дій [4]. Однак у нескладних алгоритмах такий механізм може бути надлишковим [3]. У подібних ситуаціях доцільно використовувати безпосередні команди керування виконанням, наприклад break або return [1, 4].
     Практичне застосування методу продемонстровано на функції find_product, яка здійснює пошук товару за його ідентифікатором (додаток В, розділ В.5). У початковій реалізації для фіксації результату пошуку використовувалися змінні found та result [4]. Після виявлення потрібного товару значення прапорця змінювалося, а результат зберігався для подальшого повернення [4].
     Після перетворення додаткова змінна found більше не потрібна (додаток В, розділ В.6). Якщо ідентифікатор товару збігається із шуканим, функція одразу повертає знайдений об'єкт за допомогою return [4]. Якщо відповідного елемента немає, після завершення циклу повертається None. Такий варіант реалізації скорочує кількість проміжних змінних і спрощує послідовність виконання алгоритму [1, 4]. Слайд презентації зображено на рисунку Б.6 та Б.7.

4 ВИСНОВКИ
     У ході виконання практичної роботи було досліджено три прийоми рефакторинґу, кожен з яких вирішує окрему проблему організації програмного коду.
     Під час роботи з Add Parameter було розширено можливості функції розрахунку вартості шляхом передавання розміру знижки як аргументу. За допомогою Remove Parameter усунуто непотрібний аргумент, оскільки необхідна інформація вже містилася в об'єкті замовлення. Використання Remove Control Flag дало змогу спростити алгоритм пошуку товару, замінивши додатковий прапорець безпосереднім поверненням результату.
     Виконані зміни показали, що покращення структури програми не обов'язково потребує зміни її призначення чи алгоритмічної поведінки. У розглянутих прикладах було зменшено кількість зайвих елементів, спрощено взаємодію з функціями та зроблено програмний код зрозумілішим для подальшої роботи.
